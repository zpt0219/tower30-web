## 2. 技术选型与一套代码的边界

- Vite + vanilla TypeScript，先用 DOM/CSS 做管理界面、Canvas 2D 做战场；暂不引入 React、Vue、Pixi、3D引擎等额外框架。遇到明确需求再评估。
- TypeScript启用 `strict`，并建议启用 `noUncheckedIndexedAccess`。运行时仍需验证JSON、存档和导入配置，类型断言不能替代校验。
- 单元测试采用 Vitest；浏览器流程与触控布局验收采用 Playwright。
- `src/core/` 是唯一玩法实现：战斗、空间与碰撞、动作时间轴、成长、装备、经济、掉落、楼层推进、随机数和序列化均在其中。
- 核心只能使用可移植的同步JavaScript能力和JSON数据。不得依赖 `window`、DOM、Canvas、浏览器存储、网络、Node内置模块、Vite API、Godot对象或界面组件。
- 核心通过命令改变状态，通过快照和事件提供结果。界面不直接改生命、金币、能量、库存、掉落或胜负。
- 网页依赖核心，核心不依赖网页。核心公开接口只能接收/返回可明确序列化的数据，不穿过DOM节点、函数或引擎对象。
- 先保留未来导出可嵌入JS bundle的条件。Godot接入在网页30层完成后由用户追加推进；当前通过QuickJS嵌入同一份JS bundle的独立样机已验证。没有实现TS转C++、TS转.NET编译链，也未替换原Godot项目。
- 可共用的是玩法、配表、存档模型、测试和事件协议。原生网页UI与Godot节点/动画分别实现。

## 4. 第一版玩法范围

### 4.1 楼层与资源闭环

- 仅当前30层，10/20/30层为Boss；30层通关后有完成状态。历史“百层塔”只是对话中的旧称，不恢复100层，不添加未来200层。
- 保留全部40物种定义，哪怕部分物种在当前流程中尚未获得。
- 从第1层开始，以现有两位人类、初始武器、物品和金币预算推进。初始条件从配置和当前 `TowerRun` 对照确认，不额外赠送怪兽、装备、等级或资源。
- 当前基线：240金币，3份草药、1份复活道具；两件初始武器 `traveler_sword` / `healer_staff`。这些是参考值，配置变更必须留出记录。
- 通关奖励、首次收集、魂魄和药水只能按规则发放一次。重复点击、刷新、重试、重复载入不能重复领。
- 常驻商店买卖，击败Boss后解锁新阶段商品。有限库存不能靠刷新或读档补充；穿戴中的装备先卸下才能出售，初始武器保留。
- 常驻付费旅馆，当前费用为 `InnBase + 已通过Boss数 × InnStep`，基线35 + 15×阶段。楼层、Boss和通关都不提供免费恢复。
- 人类通过战斗经验升级；怪兽只通过经验药水升级，魂魄用于升阶。
- 两位人类可穿武器、防具、饰品，怪兽不可装备；保留专用角色限制、单件装备占用和武器赋予技能的规则。
- 小/中/大药水基线提供25/100/500经验，按1/4/20小瓶单位处理。升级消耗按实际缺失经验向上取整；消耗组合和小瓶找零、退还方式以当前算法为准，不能把经验数直接显示为瓶数。
- 重试恢复该层的战前检查点，不能作为额外治疗、复制掉落或返还已确认战前交易的入口。

### 4.2 实时战斗

- 独立战场，自动普攻/自动技能，玩家选择时机释放大招。保留5首发、每方最多10名存活在场单位及补人票机制。
- 开局队伍、入场过程、单位半径、移动、碰撞、射程、弹道和命中都由核心计算。Canvas只表现结果。
- 按现有动作时间轴处理前摇、执行、后摇、冷却、控制与打断。不能把攻击简化成按秒扣血，或把弹道变成无状态的视觉动画。
- 保留当前属性模型：MaxHp、Attack、Defense、Magic、Resistance，以及暴击、穿透、急速、闪避、吸血、韧性、充能效率。能量是独立资源，上限1000；其它移动/行动参数按原定义迁移，不自行添加MP等新规则。
- 存活者跨战保留能量。回能仅来自现行出手、受击、击杀机制及其合法加成，不增加按时间自动回能。倒下成员及旅馆复活按原规则处理能量。
- 核心现使用固定 `1/60秒`，即60个逻辑tick/秒。画面通过requestAnimationFrame独立更新并插值；20Hz仅用于旧记录历史重放和C#归档对照。
- 暂停、单步与倍速改变推进的tick数或调度，不改变逻辑步长。后台页面默认暂停，不在恢复可见后突跳追算一大段时间。
- 超时、全灭、无可补人及撤回结果遵循现行核心；当前战斗超时基线300秒。

### 4.3 确定性与移植对照

- 配置版本、初始状态、随机种子、tick编号和命令序列必须可记录和复现。
- 迁移现有xorshift32随机状态，注意TS位运算的有符号结果和 `>>> 0`；源实现用uint最大值作概率分母，不能未经对照换一个常见PRNG公式。
- 明确区分源代码中的 AwayFromZero 舍入与默认 Math.Round 舍入。JS的Math.round不能一律当作等价替代，尤其半值和负数。
- 保存单位遍历、目标排序、同tick动作及命中处理顺序。明确浮点误差对比规则；不能直接宣称跨语言逐位一致。
- 迁移时用相同配置、种子、指令与原C#结果做对照；确认迁移完成后TS才是网页玩法的唯一实现。

## 5. UI已确认方向

风格维持原项目的纸张面板、字体、像素人物与物品图。参考《刀塔传奇》的手机布局组织，不复制其IP图片或付费养成系统。不要重新回到小居中窗口、巨型空白头像区、只有名称而看不到用途的物品格。

- 以1280×720横屏为基准，并实际验证20:9手机横屏。宽屏展开更多列，文字与按钮不能整体等比缩小成桌面后台。
- 每页围绕一项任务组织，把做决定需要的信息同时放在眼前。允许二级/三级确认页；不用为了“简化”把相关数据拆成许多空页面。
- 常用触控区目标至少约48 CSS像素；关键确认/返回按钮更大。字号按手机实际观感验收，不把基准画布字号机械等比缩放。
- 键盘能选中、确认、取消；触摸支持点击和纵向滑动，滑动不触发购买或选择。返回恢复筛选、滚动和焦点。

接口草案如下，可根据实际移植细化，但保持核心不依赖宿主：

```ts
interface TowerEngine {
  dispatch(command: TowerCommand): CommandResult;
  advance(ticks: number): void;
  getSnapshot(): TowerSnapshot;
  takeEvents(): readonly TowerEvent[];
  serialize(): string;
}
// 工厂和恢复函数显式传入已验证的配置/种子/存档。

```

## 7. 存档与配置编辑

- 浏览器采用独立网页存档格式与命名空间，明确schemaVersion、配置内容版本/hash、随机状态和命令序号。保留导入/导出JSON能力。
- 第一版不承诺直接读取Godot的run-v5存档，也不读写原游戏存档。未来共享的是TS核心的可移植存档模型。
- 建议由IndexedDB适配层事务保存当前档及上一份可用备份；恢复时完整校验再替换当前状态。失败显示可操作提示，提供导出，不能弹“已保存”而实际丢进度。
- 若实现战斗中保存，需要包含动作阶段、投射物、命中ID、补人票及恢复计时、随机状态等；保存后恢复不能复制一次命中或结算。未完成该能力时应明确限制保存点。
- 配置编辑使用“基线配置 → 草稿 → 校验 → 应用到新试跑”流程。旧试跑保留其配置快照/hash，不在进行中的战斗里偷偷换规则。
- 浏览器内编辑的数据先保存到浏览器或下载JSON。不能声称纯静态网页可任意覆盖本机项目文件；若以后要直接写回磁盘，单独实现明确的文件授权或开发专用服务。

- 编辑后可立即启动新试跑；布局/样式热更新与游戏状态加载分开，避免HMR重复发奖励或丢失确认中的操作。

- 核心测试覆盖伤害/舍入、最终属性、技能/状态、控制打断、碰撞、回能、首发/补人、药水换算/找零、装备占用、买卖/库存、旅馆、奖励幂等、存档及重放。
- 至少验证相同输入的稳定重放、批量推进与逐tick推进一致，以及保存中途恢复的一致性。
- 30层流程验证以正常资源开始，不靠调试授予过关；单独验证满生命但错配阵容的表现。
