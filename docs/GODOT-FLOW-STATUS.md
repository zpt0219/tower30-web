# v0.12 · 战斗侧面动画与Godot原生资源闭环

本次接通独立Godot的“战前整备 → 首发布阵 → 实时战斗 → 战报确认 → 下一层 → 30层完成页”。继续运行同一份TS核心，原Godot工程保持只读。网页版同时修正战斗素材取行；没有修改战斗规则或原始配表。

## 动画

此前战斗一直截取正面素材，仅将敌方镜像。本次使用素材已有的方向行：左1、右2、正面0；人类行间隔32像素、裁剪偏移16，怪物按自身16/32/64像素帧大小取行。移动时按水平移动方向取侧面帧，站定出手时参考目标方向，否则沿用阵营朝向；站定使用中间帧。

只有胜利且仍存活的友军切正面，按 `[0,1,2,1]` 播放行走循环。敌方、倒下者与失败场景不触发这段庆祝。庆祝只推进独立视觉时间，tick、随机、生命、能量与奖励状态都不再变化。网页与Godot共享 `src/battle-view/sprite-layout.json` 切片约定；Godot复制的是仓库已有42张角色图，不读取兄弟工程。

## 原生操作流程

- 整备：当前层敌群、核心投影的实际敌人属性、奖励、队伍最终属性/生命/能量/物品；原始240金币与两位人类开局。
- 资源：购买前明确确认，装备穿戴，怪物培养/升阶/退还药水、草药/复活羽、付费旅馆。主角最终属性和当前装备加成、技能说明同屏。价格、库存、培养费用、恢复与装备结果均由核心返回或执行。
- 布阵：点击“战前布阵”才创建战斗，最多5首发；人类锁定，怪物可选。返回整备通过核心重试命令恢复检查点。
- 战斗：自动普攻/自动技能、手动大招与补人，暂停/继续、1/60秒单步、1/2/4倍速。倍速只改变步数，绘制保留最后相邻快照作插值。
- 战报：显示实际输出、治疗、吸收、剩余生命与用时。查看战报不领金币；确认战果才执行一次finish并进入下一层。重复finish由核心拒绝，不重复奖励。
- 跨层：保留生命和能量，付费恢复；Boss后商店阶段和旅馆费用读取核心。失败/撤回可重试；30层确认后进入完成页。

原生进度使用独立目录 `tower30-web-shared-core`，自动档名为 `tower30-ts-session.json`，手动槽为 `.manual`，覆盖时保留 `.bak`。保存的是TS命令存档与UI阶段，恢复战斗默认暂停，未确认战报保留阶段。每60逻辑tick和重要命令后自动保存。主档读取失败时停止写盘，保留损坏原件；确认新试跑才将原件另外归档并重新开始。没有访问原Godot玩家存档。

调试压力场景单独标记，不计奖励、不写正式进度；测试存取仅在内存，返回正式进度时恢复进入前的完整状态。

## 实际验证

- 严格TS检查、网页静态构建通过。20个核心测试文件、91项通过，新增方向/站姿/胜利范围/大小帧与只读整备投影检查；既有正常资源30层和20Hz历史对照保留。
- 12项浏览器流程全量重跑通过：桌面1280×720、横屏1000×450各6项，覆盖实际素材行与胜利帧循环、核心tick停止、前两层、购买/取消/装备/触控、战中刷新/后台暂停/单步、损坏档恢复。首轮10通过、2项旧显示时间断言失败：三位小数时间相减可能为0.016秒。修正为精确断言tick只加1、显示误差不超过1ms后，12项完整重跑通过；没有放宽逻辑步长要求。
- Godot C#构建0警告0错误。桌面与横屏各43项原生检查通过，实际查看两个尺寸的整备、布阵、侧面战斗、正面胜利、战报、下一层、Boss结算与完成页。横屏按1000×450原生尺寸排版，关键按钮实测至少48像素。
- 原生检查通过Godot按钮/确认信号、真实物理更新和隔离磁盘槽执行。第1层在240金币预算内购买/装备后555 tick真实胜利，金币45→确认后110→付费旅馆后75；检查未确认/已确认读档、重复结算、首发、撤回重试、调试隔离。第10层真实胜利档中的存活怪物也验证正面行走循环。
- 10/20/30层使用当前60Hz正常资源记录生成的未确认战报存档，核心完整重放后通过原生确认按钮推进，验证商店阶段、付费旅馆、持久化及30条胜利记录/610金币完成页。没有宣称这组UI检查从第1层逐按钮一路操作到30层。

## 运行与交付

`npm run godot`构建并运行，默认进入战前整备。`npm run test:godot`构建并生成真实正常资源记录、Boss战报检查点并对照；随后 `npm run test:godot:ui`执行两个尺寸原生检查。本轮按同一组件命令分段执行。运行要求和存档说明见 [工程README](../integrations/godot/README.md)。
